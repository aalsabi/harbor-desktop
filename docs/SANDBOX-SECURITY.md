# Native application isolation: security scope

Harbor's opt-in launcher uses Bubblewrap for new launches made through Harbor. It does not apply a universal policy to already running applications, external launchers, desktop autostart, or arbitrary commands. Flatpak permissions remain managed separately.

By default the launch gets private namespaces, a separate persistent home per desktop application ID, an empty environment rebuilt from an allowlist, a private `/tmp`, minimal device nodes, and the session Wayland socket. Host home, session/system D-Bus paths, X11 paths, camera devices, and audio sockets are not mounted. System binaries and selected public runtime configuration are read-only. `/etc` is not exposed wholesale. Bubblewrap failure is a failed launch, never a request to relaunch outside isolation. App stdout/stderr are discarded so they cannot fill launcher log files or expose credentials through status messages.

Folder grants expose their entire directory trees as read-only or read/write. They are not per-file permissions. A sandbox app can retain copies of previously granted data in its persistent home; revoking a grant does not erase copies. Symbolic-link grant roots and symbolic-link sandbox storage roots are rejected before creating storage. Links inside exposed trees resolve within the sandbox's mount namespace. The launcher is not a defense against an attacker who already controls the host user account or concurrently replaces host-owned launch configuration.

**Network access includes host-local services.** Granting network uses the host network namespace. This permits localhost TCP and abstract Unix socket connections, including services such as X11 or D-Bus if configured to listen there. Clearing DISPLAY/DBUS variables is not an enforcement boundary against a malicious app. Keep network disabled when this separation is required. Harbor does not implement a per-destination firewall or user-space network proxy.

Audio grants the PulseAudio-compatible socket, which can include microphone and monitor capture. Camera grants expose accessible `/dev/video*` character devices. These are broad service/device grants, not narrowly scoped individual capabilities. Wayland access relies on the compositor's protocol security; this launcher does not filter compositor extensions or grant portal-mediated access. A complete security product would additionally assess seccomp, compositor protocol filtering, resource limits, and kernel attack surface.

Verification: nine focused tests pass, including an actual Bubblewrap `/usr/bin/sh` containment probe with a synthetic Wayland socket. The probe verifies isolated HOME, missing host home/system bus/X11 paths, no DISPLAY/session-bus environment, missing host `/etc/passwd`, and persistence of a write only inside the private app home. Tests do not launch user applications, connect to the real display, or modify host settings. A second integration test starts a real Qt Wayland window inside Bubblewrap against a private virtual KWin, verifies window exposure and the isolated home, and confirms the host bus is absent. It passed on the host without using the real display. Containers that prohibit user namespaces report an explicit skip. Desktop application compatibility and all granted device/service protocols are not established by these probes.

Primary references: [Bubblewrap security model](https://github.com/containers/bubblewrap#sandbox-security), [Bubblewrap command-line documentation](https://github.com/containers/bubblewrap/blob/main/bwrap.xml). Bubblewrap supplies mechanisms; Harbor is responsible for the policy constructed from them.
